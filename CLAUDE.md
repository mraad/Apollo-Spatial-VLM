# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Apollo Spatial VLM, a public continuation of [MercuriusTech/Odyseus-Spatial-VLM](https://github.com/MercuriusTech/Odyseus-Spatial-VLM) at [mraad/Apollo-Spatial-VLM](https://github.com/mraad/Apollo-Spatial-VLM) (forked, renamed 2026-10-14; a fresh clone has no `upstream` remote: `git remote add upstream https://github.com/MercuriusTech/Odyseus-Spatial-VLM.git`). A single-page demo: user uploads an image and a prompt, a VLM picks 2D targets, Depth Anything 3 (DA3) produces metric depth, and targets are lifted to 3D and shown in a Three.js point-cloud viewer. All app code is three files: `demo.py` (FastAPI backend), `index.html` + `index.js` (frontend, no build step; Three.js 0.186.1 and Spark 2.3.1 loaded from unpkg via import map; Spark needs Three.js >= 0.180).

`Depth-Anything-3/` is a git submodule of upstream ByteDance-Seed/Depth-Anything-3. Don't edit it; `demo.py` puts `Depth-Anything-3/src` on `sys.path` and imports `depth_anything_3.api.DepthAnything3`. After cloning: `git submodule update --init --recursive`.

## Two processes

1. **VLM server(s)**: any OpenAI-compatible `/v1/chat/completions` endpoint serving a vision model. Reference is vLLM with `Qwen/Qwen3-VL-8B-Instruct` on port 8012. `demo.py` reads `QWEN_URL` (default `http://127.0.0.1:8012/v1`; `normalize_vlm_url` appends the path) and `VLM_MODEL`, or `VLM_MODELS=name=url,...` for a VLM dropdown (`parse_vlm_models`; name = served model name). `VLM_TIMEOUT` (seconds, default 45) bounds each VLM call. Names containing "molmo" use the Molmo2 path: `split_target_phrases` turns the prompt into one "Point to <phrase>" request each, parsed by `parse_molmo_points`; those targets have `confidence: null`. On a GPU with room for ~56 GB of weights, `Qwen/Qwen3.6-27B` follows the demo's JSON point format far more reliably than Qwen3-VL (`eval/README.md`). `demo.py` sends `chat_template_kwargs: {"enable_thinking": false}` (Qwen3.5/3.6 think by default; others ignore it) and `run-vlm.sh` passes `--max-num-seqs` (`MAX_NUM_SEQS`, default 32) because Qwen3.6's hybrid cache can't hold vLLM's default 1024. vLLM uses CUDA graphs unless `ENFORCE_EAGER=1` (read from `.env.vlm` too); `run-vlm.sh` and `eval/serve.sh` put `.venv-vlm/bin` on `PATH` so vLLM's kernel compilation finds `ninja` (running the venv's python directly doesn't).
2. **Demo server**: `./run.sh` → `.venv/bin/python demo.py --host --port 8080 --model-dir depth-anything/DA3METRIC-LARGE --process-res 504 [--device]` (device defaults to cuda, then mps, then cpu). The DA3 model loads in the FastAPI lifespan, so startup blocks until weights are downloaded/loaded. `--model-dir` can be an HF repo id or a local HF-style directory (paths starting `/`, `.`, `~`). `--depth-model` (`DEPTH_MODEL` in `run.sh`) picks the default of `DEPTH_MODELS`: `da3`, `moge3-l`, `moge3-g`; MoGe-3 loads lazily on first use and is only offered when `moge` imports and the device is CUDA (`moge_available`).

Endpoints: `GET /` and `/index.js` (served no-cache), `GET /healthz` (device, depth models available/loaded, VLM endpoints), `GET /api/models` (dropdown choices and defaults), `POST /api/infer` (multipart `image`, optional `prompt`, `depth_model`, `vlm`).

Release version: `demo.VERSION` (0.2.1), exposed in `/healthz` and OpenAPI.

## Pipeline in `DemoRuntime.infer_image`

- Depth comes from `predict_depth` → (rgb, metric depth, invalid mask, focal, FOV, FOV source) at `process_res`. DA3: the steps below. MoGe-3 (fp16): image resized to `process_res`, metric depth and mask from the model, focal from its normalized intrinsics; an EXIF FOV is passed in as `fov_x`, else MoGe's estimate is used (`fov_source: "estimated"`). MoGe-masked pixels (sky, far background) are invalid, so a target there stays 2D-only.
- DA3 inference at `process_res` (upper-bound resize). Depth is rescaled to "metric" with `focal = estimate_focal_px(...)`, `metric = raw_depth * focal / 300`. The field of view comes from EXIF when the upload has `FocalLengthIn35mmFilm` (`exif_fov_deg`, read before `exif_transpose`, converted through the image diagonal; skipped when the pixel aspect differs from `ExifImageWidth/Height`, i.e. a crop); otherwise `DEFAULT_FOV_DEG = 60`. `meta.fov_source` is `"exif"` or `"assumed"`. Focal length changes distances along the view axis only: lateral/vertical offsets cancel it.
- Valid depth: sky/invalid mask and 1st/99th depth percentile removed (`valid_depth_mask`); invalid pixels are sent as 0. The browser builds the point cloud (`loadPointCloud`: up to `MAX_POINTS = 50000` evenly spaced valid pixels, like `np.linspace`) and the splats from that grid. Camera frame is Three.js-style: x right, y up, z = -depth.
- VLM: image downscaled to max 384 px, prompt from `custom_prompt_template` demands strict JSON `{"targets":[{label,x,y,confidence}]}` with **x/y normalized 0–1000** (Qwen3-VL's native grounding convention). `parse_vlm_targets` strips `<think>` blocks and code fences, drops `SKIP_LABELS` (floor, wall, sky…), rejects nonfinite coordinates, clamps x/y to 0–1000 and confidence to 0–1, and caps at 8. Molmo requests stop once eight targets are collected.
- Colors: `parse_vlm_targets` assigns each target a `color` (fixed per known label, else palette by index). The 2D overlay, 3D markers and target list all use that field; the frontend has no color logic.
- 3D lift: `project_target_to_3d` takes the median depth of an 11×11 patch (> 0.15 m); model-masked, nonfinite and float16-overflow depths are zeroed before projection. A target with no valid depth there is dropped from `targets_3d`.
- Response (~0.47 MB): `depth` is the full-resolution metric depth grid as base64 little-endian **float16** (`processed_size` H×W, 0 = invalid; ~0.05% relative precision, fine to 65 km), `rgb` the processed image as JPEG, plus base64 PNGs (single-channel grayscale depth preview, annotated overlay). `index.js` decodes these by field name (`decodeFloat16`, `decodeRgba`); change both sides together.
- Splats (`loadSplats` in `index.js`): the browser builds one flat Gaussian per valid depth pixel with Spark, using the same camera model as `demo.py`. Splats are oriented from neighbouring depths and fall back to camera-facing discs across depth edges (`SPLAT_EDGE`) and past `SPLAT_MAX_STRETCH` footprints. The "Gaussian splats" checkbox toggles between splats and points. Label sprites use `depthTest: false` and `renderOrder = 1`, after Spark’s default order 0, so transparent splats cannot cover them. The point-cloud position attribute reuses its Float32Array without another copy.
- Where the time goes (RTX PRO 6000 server, profiled): the VLM call is ~95% of a request (1.3–4 s); DA3 31 ms, MoGe-3 L 185 ms; all NumPy/Pillow post-processing (points, masks, previews, base64) ~13–20 ms, so CuPy wouldn't help. Measured: CUDA graphs (now the default) cut Qwen3.6-27B from 3.85 to 2.85 s per demo request on the RTX PRO 6000 server with identical output and RefCOCO accuracy (0.86); on Orin only 7.35 → 7.17 s for twice the startup, so Orin uses `ENFORCE_EAGER=1`. FP8 (`Qwen/Qwen3.6-27B-FP8`, native CUTLASS FP8 on Blackwell) then took the RTX PRO 6000 server to 1.73 s per demo request with RefCOCO 0.87. MoGe runs with `use_fp16=True` (L 165 → 91 ms, G 354 → 131 ms on the RTX PRO 6000 server; same depth, masks and FOV). The response went from 2.44 to 0.47 MB once the browser built the point cloud from float16 depth.
- `/api/infer` is a sync handler on purpose (FastAPI threadpool), so a slow VLM call doesn't block other requests; the DA3 forward pass is serialized by `DemoRuntime._lock`. Uploads over `MAX_UPLOAD_BYTES` (20 MB) get 413.
- Frontend renders VLM labels only via `textContent` (labels are model output, steerable by prompt/image text). Images without `src` are hidden by CSS and a sibling `.placeholder` shows instead; reset an image with `removeAttribute("src")`, never `src = ""`.

## Setup and run

All environments are uv venvs, no conda: `./setup.sh` → `.venv` (demo; `TORCH_BACKEND=auto` picks the torch build for the driver), `./run.sh`; `./setup-vlm.sh` → `.venv-vlm` (vLLM, pinned `VLLM_VERSION`, Linux only, separate because vLLM pins its own torch) and writes `.env.vlm`; `./run-vlm.sh` sources `.env.vlm` and starts vLLM in tmux. `setup-vlm.ps1` only writes `.env.vlm`. `run.sh` does not source `.env.vlm`; export the matching `QWEN_URL` / `VLM_MODEL` (or `VLM_MODELS`) into its environment. See the README for launch, tunnel and shutdown commands.

Platform facts (verified):
- DA3 imports `pycolmap` at load time (`utils/export/colmap.py`) though the demo never exports COLMAP. No Linux aarch64 wheel: build COLMAP from source and `uv pip install` the COLMAP repo root (pycolmap lives there); `setup.sh` stops with that hint.
- NumPy 2: MoGe requires it and DA3 declares `numpy<2`, but DA3 is installed `--no-deps` and its depth on NumPy 2 matched NumPy 1 except on pixels that already vary run to run (RTX PRO 6000 server, 7 images). `setup.sh` no longer pins NumPy; `WITH_MOGE=1` adds MoGe at a pinned commit.
- `xformers` is optional (DA3 falls back in `swiglu_ffn.py`); don't add it unpinned, it drags torch to a newer build.
- macOS: vLLM doesn't run; use Ollama (`QWEN_URL=http://127.0.0.1:11434/v1`, `VLM_MODEL=qwen3-vl:8b-instruct`). `run.sh` sets `PYTORCH_ENABLE_MPS_FALLBACK=1`.
- Jetson AGX Orin, JetPack 7 / CUDA 13 (sm_87): jetson-ai-lab `sbsa/cu130` wheels only ship sm_110/sm_121 ("no kernel image"). PyPI vLLM (0.31) has sm_87 kernels; PyPI torch runs DA3 correctly via sm_80 binaries (depth matched MPS to ~0.3% median). Unified memory requires limiting the VLM context and concurrency as well as its memory share. Verified 2026-10-14 on the dropdown branch: `WITH_MOGE=1 ./setup.sh` works (FlexGEMM builds from source, Triton 3.8 aarch64); MoGe-3 ViT-L takes 2.8 s fp32 / 1.25 s fp16 per image (DA3: 0.2 s). `Qwen/Qwen3.6-27B-FP8` serves via Marlin weight-only FP8 (no native FP8 on sm_87) at `--gpu-memory-utilization 0.7 --max-model-len 8192`, but takes ~16 s per demo request (~5 tok/s); the demo then uses 51 of 61 GB. `allenai/Molmo2-8B` is the better fit. Historical three-target timings were 5.1 s with DA3 and 9.4 s with MoGe-3 L. The 0.2.1 smoke run used eager mode with `--gpu-memory-utilization 0.55 --max-model-len 8192 --max-num-seqs 4 --max-num-batched-tokens 16384` via `eval/serve.sh`; the earlier 0.5 share / 16384 context / 32 sequences failed KV-cache allocation. `run-vlm.sh` has no environment option for `--max-num-batched-tokens`, so use the tested README recipe. The root eMMC has ~8 GB free, so keep HF downloads on the NVMe (`HF_HUB_CACHE=/data/hf-hub`).
- gc1: an inference failure came from mixed system/venv cuDNN libraries, not a missing update. Prepending `.venv/lib/python3.12/site-packages/nvidia/cudnn/lib` to the demo process’s `LD_LIBRARY_PATH` resolved it; do not change system libraries. Orin needed no override.

## Verifying changes

Unit tests (parser, colors, float16 encoding, EXIF FOV, model choice; imports `demo`, so run from the repo root with the venv): `.venv/bin/python -m unittest discover -s tests -v`. Single test: add `-k test_name`. No linter config. End to end: `curl localhost:8080/healthz`, then
`curl -X POST localhost:8080/api/infer -F image=@Depth-Anything-3/assets/examples/SOH/000.png -F "prompt=select the opera house, the harbour bridge and the red buoy"`
and check `targets_2d`/`targets_3d` and the decoded `annotated_preview`.

Automated API smoke test: `.venv/bin/python tests/smoke.py --url http://127.0.0.1:8080` exercises every advertised depth/VLM choice with the Sydney sample, with and without a prompt, and checks decoded outputs and invalid requests.

Release 0.2.1 passed 16 unit tests and six inference cases plus three invalid-request checks on gc1 and Orin; see [validation details](eval/README.md#release-021-validation-2026-10-15). A WebGL check confirmed labels draw after splats from front and side views. The local macOS unit-test import currently aborts on duplicate OpenMP runtimes in the installed dependencies; GPU validation was run remotely.

## Two-view localization research

The [research proposal](docs/two-view-localization.md) targets 10 cm positional accuracy at 5–20 m and requires **one fused Gaussian-splat scene** from both images, with measured targets and labels in the same frame. The application still accepts one image; paired inference, surface fusion and Gaussian refinement are proposed work.

Preserve these findings when implementing it:

- Use high-resolution correspondences of the same physical surface point and calibrated relative camera poses for metric localization. Two GPS camera centres leave rotation about their baseline unresolved; record attitude/control geometry and explicit height datums.
- The current `DA3METRIC-LARGE` is monocular. In the pinned DA3 API, supplied-pose alignment fails with exactly two centres; `align_to_input_ext_scale=False` does not bypass the alignment call. A tested two-view adapter is required.
- Fuse compatible surfaces in a shared metric frame before constructing/refining Gaussians. Keep Gaussian footprint/opacity separate from positional uncertainty, and preserve measured anchors during appearance optimization. Retain the existing labels-after-splats render order.
- Depth/geometry fusion is required. Generative diffusion is optional completion: generated views are not independent geometric evidence and do not automatically become an exportable Gaussian scene.
- Compare explicit fusion using Spark with DA3 Giant/Nested Gaussian output, DepthSplat, MVSplat and ReSplat; the proposal links primary sources. None has been benchmarked for fused-scene accuracy here.

The CPU-only experiment is `eval/two_view_localization.py`; run its 10 focused tests with `.venv/bin/python -m unittest discover -s tests -p 'test_two_view_localization.py' -v`. It avoids importing the live demo or torch. Saved [results](eval/results/two-view-localization.json) are point-localization measurements, not Gaussian-fusion results, and do not establish the 10 cm requirement.
